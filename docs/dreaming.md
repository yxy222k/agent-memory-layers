# 离线整理（dreaming）

会话中随手写的东西一定会有错、会过期、会重复。整理环节的存在，是把这些早发现，
**在不影响白天的前提下**。

名字叫 dreaming 是因为它模仿睡眠期的记忆巩固：不产生新经验，只重组已有经验。

## 第一原则：产出 patch，不许直接改

```
离线任务读 ① → 产出 memory/dreaming/<date>.patch + change-log.md
   → 人看 git diff，逐条 accept / reject
   → 合并后 commit（message 用 change-log 摘要）
```

为什么这条不能省：

- 整理的错误是**静默且永久**的。一条错笔记不会报错，只会被之后每个会话信任。
- 本地/离线跑得再便宜，也必须留一道人工闸门。`git diff` 就是那道闸门。
- 一旦允许直接改文件，你就失去了唯一能发现错误的机制。

如果整理跑在夜里，这条更重要——**出错时你已经睡了**。

## 六个通用动作

按顺序，前面的会改变后面的输入：

1. **纠错** —— 每条新笔记回到 ① 层找证据；不符的改写并标 `[corrected: <来源>]`
2. **判失效** —— 环境/版本变化导致不成立的，标 `stale`，从注入层移除
3. **合并** —— 同主题多条合成一条，保留全部证据链接
4. **补链** —— 地图里指向不存在页的链接，改指已有页或建最小页
5. **升降级** —— 被引用 ≥3 次的笔记，提炼一句进注入层；细节留 ②
6. **出摘要** —— 写 change-log：改了什么、为什么、需人工确认的 ≤5 条

## 三个领域专属动作

### 版本失效扫描（设备/软件类产品必做）

产品有新版本发布时，全库重判一遍：所有 `applies_to.version` 区间不覆盖新版本的笔记，
逐条判 **保留 / 更新区间 / 标 stale**。

**这是这类记忆库不腐烂的唯一办法。** 一条不带版本区间的规则，升级之后就是定时炸弹：
它不会报错，只会让所有人按旧结论干活。所以宁可写"仅 3.1–3.4 有效"，也不要写"一般情况"。

### 晋升（多租户时）

同一现象在 ≥2 个客户/项目出现 → 进晋升候选，附各自的证据链接和差异。
人工确认后才进全局库。

**晋升的产物必须是抽象的规则，不是某个客户的案例原文。** 把客户 A 的现场记录搬进全局库，
既泄露又误导。

### 冲突检测（研发线必做）

两条实验结论互斥时，标 `conflict`，并给出"能裁决它们的最小实验设计"。
不要自动选一个——研发线里最有价值的信息往往就是"这两个结果打架"。

## 节奏

- **每天或每 20 个会话**一次，跟着实际写入量走。
- 版本发布后**额外**跑一次版本扫描。
- 每月做一次人工抽检：随机 10 条 `verified`，回第 ① 层核对。抽检发现错误，说明整理环节的
  纠错动作失效了，先修流程再加频率。

## 提示词

见 [`../templates/dreaming/prompt.md`](../templates/dreaming/prompt.md)。核心硬约束是这五条：

1. 不得新增任何没有证据的"事实"
2. 不得删除笔记，只能标 `stale`
3. 不得把笔记原文成段搬进地图
4. 客户/项目名、配方、良率不入库；写前脱敏
5. 不得把某个租户的约束写成全局规则

## 一个容易忽略的收益

整理环节顺手产出**速查卡**：从全局规则 + 某租户的约束，生成该客户专用的 1 页纸
（"这台设备在这个现场，只有这 8 件事要做"）。

这件事的成本几乎为零，但它是这套系统里**唯一直接给人用**的产物——记忆不只是给 agent 用的。
