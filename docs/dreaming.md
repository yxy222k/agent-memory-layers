# 离线蒸馏（Dreaming / Cronjob）

白天做实验、调设备、排故障时，注意力应该放在主任务上，随手留下的记录一定会有残缺、重复或过时。离线蒸馏的作用，是在**不打断白天工作的前提下**，利用空闲算力回看原始流水，把零散经验织成结构，并把错误和过期记忆早点揪出来。

---

## 一、 双确认闸门：蒸馏前轻筛 + 蒸馏后审 Diff

硬件与实验研发不能无脑跑全自动夜间覆盖——实验台上一天会产生不少「光纤法兰没拧紧」「暗室没关灯」的废记录，直接蒸馏只会提炼出噪音；而蒸馏一旦静默改错规则，后续每次会话都会盲目信任它。

因此流程固定为**一前一后两道人工确认**：

```text
[阶段 1：蒸馏前轻筛（30 秒）]
Cronjob 扫描新增 transcripts/ 与 4_anomalies/ → 生成待处理清单（经 lark cli 或终端推送）
   → 人勾掉废实验、确认哪条异常已真正结案
   ↓
[阶段 2：隔离工作树蒸馏]
scripts/dream-worktree.sh 拉起独立 git worktree 分支 → 运行离线整理 Agent 直接编辑文件
   → 脚本自动导出真实 git diff + change-log.md（待重点确认项 ≤5 条）
   ↓
[阶段 3：蒸馏后合并]
人审阅 git diff，逐块 accept / reject → 合入主分支
```

> **工程细节**：不要让大模型手写 `.patch` 文本（行号极易算错导致 `git apply` 失败）。让 Agent 在隔离的 `git worktree` 中正常改文件，由脚本跑 `git diff` 才是零故障做法。

---

## 二、 核心飞轮：第四层（排故）反向驱动前三层进化

这套系统里最核心的知识生长机制，不是凭空摘抄，而是**当 `4_anomalies/` 中有一条异常完成归因结案（`open → resolved`）时，离线蒸馏必须沿着四个方向做连锁巡检**：

1. **向 `1_theory/` 巡检（修正模型边界）**
   这次实测根因是否证伪了现有物理/仿真模型的某个理想化假设？（例如：原相位解算假设光源中心波长恒定，实测低电流下 SLD 漂移导致系统性相位跳变 → 在对应机理页补充适用边界与反例链接）。
2. **向 `2_calibration/` 巡检（补齐 SOP 与刷新器件档案）**
   - 是否暴露了某类器件入库标定时漏测的指标？（→ 提议加入 `2_calibration/sops/` 必检清单）
   - 是否证明某支在役器件（如 `#SLD-1310-03` 或某台光谱仪）参数已漂移失准？（→ 将旧基线标 `stale`，关联新标定记录）
3. **向 `3_skills/` 巡检（修补操作与存储坑）**
   异常是否源于串口指令时序不当、CLI 参数误用，或数据存成 `csv` 丢失精度/时间戳（本该用 `hdf5`/`pcap`）？（→ 提议修订对应 `SKILL.md` 的防呆说明）
4. **向全库旧结论巡检（推翻与更正）**
   全文检索所有曾依赖旧错误前提的实验结论、未解异常或报告口径，逐条标记 `[corrected: <结案单ID>]` 或改标 `stale` / `refuted`，列入人工必审摘要。

## 三、 日常例行整理动作（按顺序执行）

除了排故触发的跨层反哺，每次例行蒸馏按以下顺序处理增量记录：

1. **草稿提炼** —— 扫描已确认有效的 `transcripts/`，将系统里查不到、可复用的新现象提炼为 `hypothesis` 或 `4_anomalies/open/` 复现单。
2. **对账纠错** —— 新增记录一律回到 `transcripts/` 核对原始数据/伴生卡；与事实不符的改写并标 `[corrected: <来源>]`。
3. **合并去重** —— 同一主题或同一故障模式的零散记录合并，保留全部原始证据锚点。
4. **图谱补链与瘦身** —— 修复 `1_theory/` 中指向不存在页面的断链；检查 `1_theory/` 总字数是否小于底层材料，剔除大段原文照搬。
5. **引用统计与注入层升降级** —— 根据脚本统计的 `[ref: <id>]` 真实引用次数：高频（如 ≥3 次）且跨场景关键的条目提炼一句话升入 `MEMORY.md`；`MEMORY.md` 逼近 200 行/25KB 上限时，将最久未被引用的条目下沉回各自目录。

## 四、 三个专项扫描（按事件触发）

### 1. 版本/硬件切换失效扫描（发版或换件必做）
软件发布新版本，或实验台更换核心光电器件（光源、光谱仪、探头）后，全库扫描 `applies_to` 字段：不覆盖新版本/新硬件组合的条目，逐一判定 **保留扩展区间 / 拆分为版本分支 / 标 `stale`**。

### 2. 多租户共性晋升（多现场交付时启用）
同一现象或排查规律在 **≥2 个独立租户（`tenants/*`）** 复现 → 提取为候选全局规则。**晋升产物必须是脱敏后的抽象机制与判据**，严禁把客户 A 的现场原始配置、配方或良率搬进全局库。

### 3. 互斥结论裁决设计（研发线必做）
当两次实验记录或两条机理推导结论互斥时，**禁止大模型私自折中或挑一个顺眼的保留**。必须显式标为 `conflict`，并在 `change-log.md` 中给出**能裁决二者的最小验证实验设计**（固定哪些变量、测哪个档位）。

---

## 五、 运行节奏与抽检

- **常规频率**：每周一次，或每累计 15–20 条有效 `transcripts` 触发一次（小步快跑比攒三个月大扫除更容易审 Diff）。
- **事件触发**：重大排故结案、软件发版、核心器件更换当天额外跑一次专项蒸馏。
- **月度真值抽检**：每月随机抽 10 条 `verified` 记忆，人工顺着 `evidence` 回查 `transcripts/` 原件。一旦发现无据脑补或修错，先停定时任务修 Prompt，再恢复运行。
