# 系统架构：控制面 × 正交双轴工程记忆

## 为什么传统 Agent 记忆在复杂工程研发中会失效

现有的 AI 记忆方案大多只做对了一半：

1. **工具内置记忆 / 单机扁平笔记**：绑死在单一客户端或单台电脑上，换机器、换工具即失忆；且把「个人交互偏好」「本机编译器路径」和「具体硬件台架标定值」混成一锅，多工具并发覆写极易互相踩踏。
2. **单维浓缩分层（`原始流水 → 笔记 → Wiki → 常驻提示词`）**：适合纯文档问答，但一旦进入**机器人、嵌入式/FPGA、精密仪器、工业自动化、自动驾驶或软硬件协同系统**就会迅速腐烂：
   - **第一性原理控制方程**与**某支特定传感器的零偏温漂表**半衰期相差几个数量级；
   - **总线指令、`.hdf5`/`.pcapng` 存储结构、对外报告脱敏规范**属于程序性技能，平时不该白占推理上下文；
   - **排故记录**在未破案时没有机理可写（只能保复现），一旦破案又必须反向修正仿真模型边界、补齐入库标定漏项、推翻旧结论。

因此，`agent-memory-layers` 采用 **「轻量跨机控制面 + 产品正交双轴内核」** 架构，同时支持**单项目嵌入（Standalone）**与**多机多产品总控（Hub）**两种部署形态。

## 一、 两种部署形态，同一套协议内核

### 形态 A：单项目嵌入模式（`standalone`）
直接挂载在单个工程仓库的 `memory/` 目录下，零全局侵入，开箱即用：

```text
<project-repo>/memory/
├── aml.json                  # 容量预算与安全配置
├── AGENTS.md + MEMORY.md     # ④ 常驻注入阶（版本 + 在役资产编号 + 安全红线 + 热路由）
├── 1_theory/                 # ③ 科学机理、数学建模与仿真成立边界
├── 2_calibration/            # ② sops/ 标准标定规程 + assets/ 单件资产实测包线
├── 3_skills/                 # ③ 按需挂载的 SKILL.md（连接/CLI/数据格式/脱敏/自动化）
├── 4_anomalies/              # ② open/ 最小复现快照 + resolved/ 归因与四向反哺记录
├── transcripts/              # ① 只追加原始事实底座与多模态伴生索引卡
└── tenants/<code_name>/      # 物理隔离的客户/现场分区
```

### 形态 B：多机多工具多产品总控模式（`hub`）
用一个私有 Git 仓库统管你名下所有开发机、实验室工控机、云服务器与各类 AI 客户端，同时物理隔离多条产品线的工程记忆：

```text
<private-memory-hub>/
├── aml.json                        # 全局预算、工作区路径→产品自动路由表、公开远端防推名单
├── 0_control/                      # [第 0 层：跨机跨工具控制面]
│   ├── rules.md                    # 负责人亲定的最高行为与安全红线（≤ 4 KB）
│   ├── INDEX.md                    # 全局产品线一句话状态快照与入口表（无工作区时挂载）
│   ├── shared_skills/              # 跨产品通用按需技能（工程绘图、通用自动化等）
│   └── hosts/<hostname>/env.md     # 按“物理主机”记录 OS/工具链/网口事实（同机多工具共享）
├── inbox/                          # 在线会话零冲突只追加暂存区
└── products/<product-slug>/        # 每条产品线独占一套完整双轴记忆树（与形态 A 同构）
```

> **为什么按 `hosts/<hostname>/` 切环境、按 `products/<slug>/` 切知识，而不是按聊天工具切目录？**
> 同一台工控机上的 Claude Code、Codex 和 Antigravity 面对的是完全相同的内核、编译器、网卡与串口——按物理主机存一份 `env.md` 彻底消除了跨工具重复维护；而工程事实天然归属于产品线而非某个聊天窗口。

## 二、 产品内核：正交双轴矩阵（业务四域 × 加工四阶）

### 横轴：四个工程业务域（存什么、半衰期多长）

| 域 | 目录 | 承载内容 | 半衰期 | 生产与审阅机制 |
|---|---|---|---|---|
| **① 科学机理与模型** | `1_theory/` | 物理/数学/控制定律、文献图谱、建模与仿真边界 | 极长（仅当假设被实测突破时修订） | 前沿推理模型多 Agent 并发（一人一页 + `_RESEARCH_LOG.md`）+ 人工共审 |
| **② 标定规程与资产档案** | `2_calibration/` | **SOP**：准入/定检必测核查单；**Asset**：单序列号实测基线与安全包线 | SOP 长；Asset 绑定**唯一资产 ID 与校准期** | 人定规程；执行端按强 Checklist 核查留证 |
| **③ 操作技能（Skill）** | `3_skills/` | 设备总线连接、源码与 CLI、数据格式、报告脱敏、自动化通知 | 中（随工具链与版本演进） | 标准 `SKILL.md` 按需挂载，平时 `0 token`；**凭证零明文** |
| **④ 异常与排故账本** | `4_anomalies/` | **Open**：可复现未解异常包；**Resolved**：归因结论、负结果与跨层反哺单 | 动态（驱动前三个域进化的发动机） | 在线轻量抓复现；结案后由离线蒸馏反向修正 ① / ② / ③ |

#### 为什么要把 `2_calibration/` 拆成 `sops/` 和 `assets/`
工程现场最高频的混乱，是把「测试动作规范」和「单件硬件的个体脾气」揉在同一份笔记里：
- **规程（`sops/`）**回答「拿到一类模块必须测哪些指标、留哪些证据」；
- **档案（`assets/`）**回答「编号 `#SENS-24B-07` 这件模块实测零偏、饱和线和过载硬极限是多少」。更换备件后 SOP 不变，只需切换当前在役 `asset_id` 档案，旧件标 `stale`。

### 纵轴：四个加工与加载阶（控检索成本、防污染）

```text
④ 常驻注入阶  AGENTS.md + MEMORY.md (+ Hub 0_control)  会话必载，MEMORY.md 硬上限 ≤ 200 行 / 25 KB
③ 结构导航阶  1_theory/ + 3_skills/                    机理综合图谱与按需技能，导航体积 < 底层记录 30%
② 判断与基线  2_calibration/ + 4_anomalies/            强制带证据锚点、状态机与 applies_to 版本/资产边界
① 事实底座阶  transcripts/                             原始实验流水、工单与多模态伴生卡；只追加、不篡改
```

## 三、 五级优先级裁决链（锁死红线 + 参数按特指度覆盖）

当不同层级的描述出现表面冲突时，严禁模型自行折中猜测，严格按「**安全红线自顶向下不可覆盖、工程参数按现场与个体特指度就近优先**」裁决：

1. **安全、保密与行为死红线**（`0_control/rules.md` + 硬件瞬时损坏极限 + 凭证零落盘 + 禁跨租户泄密）→ **最高权威，任何层级不可突破**
2. **本机物理环境事实**（`0_control/hosts/<host>/env.md`）→ 本机编译器、解释器、网卡与端口绑定以此为准
3. **客户现场特殊口径**（`tenants/<code_name>/AGENTS.md`）→ 现场验收判据、停机窗口与术语映射优先于产品通用惯例
4. **单件在役资产实测基线**（`2_calibration/assets/<asset_id>.md`）→ 当前序列号的实测传递曲线优先于同型号手册标称值
5. **产品通用机理、标准规程与默认技能**（`1_theory/`、`2_calibration/sops/`、`3_skills/`）

## 四、 两阶段写入门槛与六态生命周期

在排故进行中强迫模型填写完整物理根因，只会逼出未经证实的脑补；而完全不设晋升门槛又会让错误判断永久污染知识库。因此采用**宽进严升**：

1. **在线轻量捕获（只追加、零冲突）**
   - 仅允许向 `inbox/`、`transcripts/` 或 `4_anomalies/open/` 新建唯一命名的独立文件（`aml capture`）。
   - 不要求当场写清底层机理，只要求保留**定量现象 + 软件版本 + 在役资产 ID + 原始数据/截图指针**。
2. **离线严格固化（双闸门 Dreaming + 零 Token 机械校验）**
   - 升格为 `verified` 或归档结案时，强制具备排他证据链（`evidence`）、适用版本/硬件区间（`applies_to`）与失效反例，并通过 `aml check` 静态规则核验。

### 状态机：彻底分开「证伪负结果」与「过期失效」
- `open` / `hypothesis` —— 待破案异常或单次待验证假设，必须附带可复现条件或最小证伪实验。
- `verified` —— 经排他实验或独立复测确认成立的规律、基线或结案归因。
- `refuted` —— **已被实验证伪的方案（负结果）**。研发中「某滤波/结构方案试过不通且引入某副作用」具有极高避坑价值，**长期保留并鼓励正面引用拦截重复试错**。
- `stale` —— **曾经成立，但因固件升级、换件重标或配置变更不再适用**。保留历史文件不删，但强制从 `MEMORY.md` 与 `INDEX.md` 移除（由 `aml check` 硬拦截）。
- `conflict` —— 两条实测或机理结论互斥，等待最小裁决实验定案。

## 五、 多模态伴生索引卡与三条安全硬红线

### 大体积二进制与多模态证据挂接
记忆仓库保持纯文本轻量 Git 结构，不直接混入数百 MB 的 `.hdf5`、`.parquet`、`.mcap`、`.pcapng` 或高清原图：
- 原件按 `3_skills/data-schema/SKILL.md` 命名规范存入 NAS / 对象存储 / Git LFS；
- 在 `transcripts/` 建立轻量 `.md` 伴生索引卡，记录版本、资产 ID 组合、关键参数、原件路径与 SHA256 前缀，以及一两句物理装夹状态与界面关键读数速记。

### 三条安全硬红线（由 `aml check` 与 `pre-push` 双重守护）
1. **凭证零明文**：私钥、API Token、登录口令严禁进入任何 Markdown 或提交信息，统一引用环境变量。
2. **多产品与多租户目录白名单检索**：通过 `aml search [--product <slug>] [--tenant <code>]` 限定检索域，禁止跨客户现场裸跑全库搜索。
3. **私有实例防误推公开远端**：私有库开启 `"private_instance": true` 后，`pre-push` 钩子自动拦截向公开模板仓库的任何推送。
