# 为什么是四层

## 问题

知识库的失效很少是"记得少"，常见有三种：

1. **检索成本失控**——原始记录和结论混在一起，找一条要翻几百条，于是没人翻。
2. **结论没有证据**——三个月后看到一句"某型号测不准"，不知道当时是什么条件、是否已验证。
3. **地图比国土还大**——把所有材料"整理"成 wiki，结果 wiki 比原材料还长，抽象度为零。

四层结构分别对应这三件事。

## 四层各自的职责

```
④ 注入层   每次会话都加载          极小，只放"每次都必须知道"的
③ 表示层   wiki，提供导航           必须比它索引的材料小
② 笔记层   判断、规则、陷阱          每条带证据，可被判失效
① 事实层   原始记录                只追加，是纠错的唯一基准
```

### ① 事实层

工单原文、实验记录、会话日志、现场照片的索引。**只追加、不改写。**

这是整套系统的地基：整理环节要判断"这条笔记对不对"，唯一的依据就是回到第 ① 层。
一旦第 ① 层被"顺便润色"过，纠错就退化成互相引用。

### ② 笔记层

人（或整理环节）从第 ① 层提炼出的**判断**。四类最值钱：

| 类型 | 回答什么 | 例子形态 |
|---|---|---|
| 规则 | 什么条件下该选什么 | "AR>8 时不要用 X 模型" |
| 陷阱 | 看起来像 A 其实是 B | "残差正常但重复性差，先查载台" |
| 因果 | 症状 → 根因 → 证据 | "底部覆盖不足 → 电镀空洞" |
| 计划 | 上次做到哪、下一步试什么 | 跨会话续命 |

状态机是硬要求：

- `verified` —— **≥2 次独立证据**。单次观察一律 `hypothesis`。
- `hypothesis` —— 必须写"怎么验证它"，否则不是假设，是许愿。
- `stale` —— 环境变了标失效，**不删除**。删掉的知识会以更贵的方式重新学一遍。

每条笔记必须有**「反例 / 边界」**段。没有边界的规则，将来一定会误导人。

### ③ 表示层

wiki 的唯一作用是"让你不用翻几百条笔记就能定位"。所以它有两条硬约束：

- **必须小于被索引的材料**。一旦 wiki 长到和原文一样大，它就是负担而不是索引
  （真实案例：一份 10 文档 115 KB 的语料，生成了 203 KB 的 wiki，1.77 倍，等于零抽象）。
- **一页一主题，必须有链接**。孤立页等于死页。

### ④ 注入层

每次会话都加载，所以它最贵。只放三类：

1. 角色与红线（写错了会全盘带错）
2. 当前环境（版本号、部署位置、在做什么）
3. 索引（"想找什么，去哪一页"）

**硬上限**（比如 200 行 / 25 KB）。超了就下沉到 ③，不要靠"精简措辞"续命。
注入层膨胀是最常见的死法：写得越长，遵循度越低。

## 写入门槛：三问

新知识进来之前问三句，**都过才写**：

1. 以后还会再遇到吗？
2. 屏幕上、系统里查得到吗？（查得到就不写，写下来只会多一份会漂移的副本）
3. 我能给出证据吗？（给不出 → 标 `hypothesis`，或干脆不写）

## 什么时候不该用它

- 一次性任务。
- 能从系统实时查到的事实（库存、参数表、日志、当前读数）。这些**一层都不要放**。
- 纯个人偏好——那属于 agent 记忆，不属于业务知识库。

## 两种记忆不要混

这是实践里最容易犯错的地方。有两个长得很像、但职责完全不同的东西：

| | agent 记忆 | 业务记忆（本仓库） |
|---|---|---|
| 回答 | "我该怎么干活" | "这条产品线知道什么" |
| 写入者 | 每个 agent 写自己的目录 | 人 + 整理环节 |
| 结构 | 规则 / 共享 / 每-agent | 四层 + 租户分区 |
| 整理机制 | 蒸馏（人工触发，合并进共享区） | 离线整理（定时，产出 patch） |
| 隔离维度 | 按 agent / 机器 | 按客户 / 项目 |

混在一起的后果是双向的：业务数据污染 agent 的常驻层；业务库失去租户隔离，
而且"谁有权改共享记忆"变得含糊。

推荐接法：业务库放产品仓库，agent 记忆库只放**方法、项目快照、决策**三样，并写清指路。

## 一个反直觉的结论

这套东西里最贵的不是存储，是**策展**。

能力强的模型和弱的模型差别，往往不在会不会写，而在**克制**：从"什么都记"到"只记屏幕外的东西"，
再到"记规则 + 依据 + 陷阱"。存储免费的时代，判断力才是稀缺资源。
