# agent-memory-layers

> 给一条产品线或业务线建一套能长期用下去的长期记忆：四层结构、写入闸门、离线整理。

一个纯 Markdown 的记忆库模板。不依赖服务器、数据库或向量库，一个 git 仓库就够。

## 为什么需要它

随手攒的知识库，三个月后就没人看了。原因通常不是记得少，而是**三层混在一起**：
原始记录和结论堆在同一层，找一条要翻几百条，于是没人翻。

四层结构解决两件事：**检索成本**（每层只放它该放的东西）和**污染**（原始记录永远可回溯，
结论永远带证据）。抽象度自下而上递增，地图永远比它索引的材料小。

## 四层

| 层 | 放什么 | 硬约束 |
|---|---|---|
| ① 事实 | 原始记录：工单、实验记录、会话、日志 | 只追加、不改写，是纠错的唯一基准 |
| ② 判断 | 规则、陷阱、验证过的因果 | 每条带来源；分 `verified` / `hypothesis` / `stale` |
| ③ 地图 | wiki：把知识组织成可导航的索引 | 必须**小于**它索引的材料，一页一主题 |
| ④ 注入 | 每次会话都加载的极小上下文 | 硬上限（行数/字节），超了就下沉 |

**不要跳层**：没有 ① 的 ② 是猜测，没有 ② 的 ③ 是摘抄。

## 三条最关键的规则

1. **写入门槛三问**（都过才写）：以后还会遇到吗？系统里查得到吗？能给出证据吗？
2. **整理放离线**，且**必须产出 patch，不许直接改文件**——人看 `git diff` 再合并。
   失去 diff 就失去这套系统唯一的纠错闸门。
3. **一人一文件**。多人多 agent 同时写同一文件必然互相覆盖，合并交给整理环节。

## 它是怎么长出来的

这套结构来自对一个真实产品线的实践：一套精密测量设备（服务端 + 算法 + 现场服务），
把散在工单、实验记录和几个 AI 助手记忆里的知识收进一个库。

过程中最有价值的发现，恰好都是"文档说的和实际跑的不一致"：

- 仓库文档写着某个算法"未部署"，现场日志证明**已经跑了三周**。跨那个日期对比数据等于换口径。
- 一条"看起来像算法不准"的偏移，换成另一支探头后消失了 74%——根因在硬件不在算法。
- 一份补偿表被当成"已定位的根因"并默认打开，后来发现它绑定的那套配置早已换掉，
  套上去反而放大三倍误差。

**所以第 ① 层必须是原始记录，不能是文档。** 文档记录意图，原始记录记录事实。

## 快速开始

```bash
git clone <this repo> memory-kit
cp -r memory-kit/templates/* <your-product-repo>/memory/
```

然后：

1. 填 `memory/AGENTS.md`：产品、环境、红线、**软件版本**（版本是设备类产品笔记的前提）
2. 手写 10–20 条种子笔记——**空库跑整理只会整理出空话**
3. 接一个离线整理任务（`templates/dreaming/prompt.md`），产出 patch 而不是直接改
4. 用 `templates/eval/cases.jsonl` 的格式出 30–50 道题，做一次有/无记忆的对照

## 目录

```
templates/            复制到你的产品仓库
  AGENTS.md           ④ 注入层：角色、环境、红线
  MEMORY.md           ④ 索引（≤200 行）
  notes/_TEMPLATE.md  ② 笔记模板
  wiki/index.md       ③ 地图入口
  wiki/_TEMPLATE.md   ③ 页面模板
  tenants/            按客户/项目隔离的分区
  transcripts/        ① 事实层
  dreaming/prompt.md  离线整理提示词
  eval/cases.jsonl    评测题集格式
docs/
  why-four-layers.md  方法论与边界（含"两种记忆不要混"）
  dreaming.md         离线整理：PR 模式、版本失效扫描、晋升、冲突
  metrics.md          评测：四组对照与指标
```

## 和 agent-memory-nest 的关系

[agent-memory-nest](https://github.com/songth1ef/agent-memory-nest) 管的是「**agent 怎么干活**」：
规则、共享记忆、项目快照，按索引加载，每个 agent 只写自己的目录。

这个仓库管的是「**某条产品线知道什么**」：工单、实验、版本矩阵、客户口径。

两者形状不同，**不要混在一个库里**：巢的常驻层会被业务数据污染，业务库会失去租户隔离。
推荐的接法：

| 放哪 | 放什么 |
|---|---|
| 产品仓库 `memory/` | 整个四层记忆库 |
| 巢的 `workflow/` | 方法（本仓库 `docs/`） |
| 巢的 `projects/` | 一句状态快照 |
| 巢的 `decisions/` | 为什么这么分 |

## 不做什么

- 不做服务端、不做向量库、不做 GUI。检索先用 `rg`。
- 不做权限控制层。租户隔离靠目录边界，权限靠 git 托管方。
- 不替你判断业务问题。这套东西只保证：知识不会因为"没人记得写"而丢掉。
